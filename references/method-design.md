# 方法与能力设计

## 从材料推导方法

先看材料能支持哪一级结论。规范支持适用条件内的规则；成功记录支持被观察的结果；未执行设计只支持拟议方案。记录原始来源、版本或快照与未知，不把构造示例当真实业务记录。

从具体决策反推证据：什么情况适用？需要知道什么？哪种新证据会改变选择？如何检查完成？何时无法判断？把缺失、冲突、不可判定和不适用分开。没有可靠方法时设计能区分候选方法的最小实验，保留假设身份。

提炼模式：对齐多个案例的共同决策；保留改变分支的差异；对一次性步骤寻找不适用反例。明确行为来自正式要求、案例观察还是开发者建议。只凭执行后结果好转不能确定原因，多个变量同时变化时尤其如此。

改进模式：先复现具体失败，再判断是方法、实现还是评价有问题。用户只改描述或局部规则时，不自动重做整套方法研究。

## 最小方法卡

需要复杂设计时记录下面信息；简单任务可直接写在工作记录中。

| 信息 | 要回答的问题 |
| --- | --- |
| 适用边界 | 哪类请求和输入可处理？什么条件改变路径？ |
| 必要证据 | 来自什么来源、对象、时间或版本？缺失怎样处理？ |
| 决策与反证 | 证据如何改变行动？什么会推翻当前解释？ |
| 结果检查 | 什么真实产物或状态证明完成？ |
| 异常与停止 | 冲突、依赖失败、无法裁决时怎样继续或停止？ |
| 依据与成熟度 | 来源支持、观察、假设或已测试？测试到哪一层？ |

领域标准不明且影响正确性时查询权威来源或向用户澄清；不要用流畅措辞补齐专业真值。规则相冲突时记录冲突和适用范围，别静默选对实现最方便的一条。

新建或实质更新的专业 Skill，应把方法卡结论写入 [Skill 设计框架](design-framework.md) 的“方法、决策与反证”，并把范围、能力和验证结论写入对应章节。方法卡是推导工具，不替代初始化前的设计门禁。

## 能力分配

| 承担者 | 内容 | 核验点 |
| --- | --- | --- |
| Skill 指导的 Agent | 分支选择、取证顺序、上下文判断 | 判断能否由证据支持 |
| 参考资料 | 可检索的规则、版本知识、例外 | 来源、更新条件与发现路径 |
| 脚本 | 稳定读取、转换和机械检查 | 输入契约、错误语义、真实副作用 |
| 外部工具 | 系统读取或操作 | 实际存在、授权、对象绑定与失败状态 |
| 运行环境 | 执行、隔离、保存、审批 | 当前环境是否提供，不能靠文字假装实现 |

依赖分为已验证可用、已声明未验证、缺失、不适用。为必要取证动作写清输入对象、返回事实、来源/版本、错误语义与使用条件；只保留本领域必要字段，别把 HFSS 或任何单领域身份结构复制为通用要求。

开发审查评判目标 Skill 的方法与行为。若业务任务自身需要结论审查，把它另行设计成目标 Skill 的运行步骤；开发审查不能替代每次业务判断。
